# Decisions

## Статусы

- `ACCEPTED` — явно подтверждено владельцем продукта или является правилом процесса из задания.
- `PROPOSED` — рекомендация аудита; реализация запрещена до согласования.
- `REJECTED` — рассмотрено и отклонено.
- `SUPERSEDED` — заменено более новым решением.

## Принятые решения

### ADR-000 — сначала анализ, затем согласование

- Статус: `ACCEPTED`
- До закрытия архитектурного gate запрещён executable production-код. Gate считается закрытым только после готовности согласованной архитектуры (`G4`) и подробного плана реализации с проверяемыми задачами (`G5`).
- Разрешены документация и воспроизводимые прототипы/benchmark-код в изолированном каталоге `prototypes/`. Production packages не импортируют его, а сам прототип не считается началом реализации.
- Production-разработка начинается только после моего отдельного явного разрешения, даже если checklist уже заполнен.
- Явное разрешение — однозначная команда начать production-разработку в Codex. Факт разрешения, дата и начатый этап фиксируются в [CHANGELOG_ARCHITECTURE.md](CHANGELOG_ARCHITECTURE.md).
- До этого разрешены только необходимые security/infrastructure исправления, которые не меняют бизнес-логику; причина каждого исключения фиксируется в changelog.
- Причина: неопределённые правила меняют границы агрегатов, безопасность и жизненные циклы.

### ADR-001 — спецификация остаётся неизменным источником требований

- Статус: `ACCEPTED`
- `/Users/skh/Downloads/specifikaciya_socialnaya_karta_telegram.docx` не изменяется без моего прямого разрешения.
- Более новое решение со статусом `ACCEPTED` заменяет только конкретную противоречащую часть спецификации; остальные требования продолжают действовать.
- Если два решения со статусом `ACCEPTED` противоречат друг другу, разработка затронутой части останавливается до моего ответа. Ни дата, ни тип `PD`/`ADR` сами по себе не определяют победителя.
- В публичном репозитории хранится полная версионируемая Markdown-копия требований без секретов, персональных данных, production-конфигурации и закрытых anti-fraud/reputation правил.
- Для требований ведётся traceability matrix: ID, источник, текущий статус и заменившее решение.
- Полная копия хранится в [SOURCE_SPECIFICATION.md](SOURCE_SPECIFICATION.md), матрица — в [REQUIREMENTS_TRACEABILITY.md](REQUIREMENTS_TRACEABILITY.md).
- После полного аудита создаётся читаемый снимок актуальной спецификации `v1.0`. Он объединяет действующие правила для чтения, но не заменяет исходную спецификацию, `PD`, `ADR` и матрицу трассировки как источники отдельных решений.
- До каждого функционального среза связанные пакеты из 28 разделов матрицы раскладываются на атомарные acceptance criteria и тесты. Это не разрешает молча додумывать отсутствующие правила.
- Production-секреты хранятся в secret manager. В Git остаются только имена переменных и безопасные примеры.
- Противоречия фиксируются в `OPEN_QUESTIONS.md`, решения — здесь и в `PRODUCT_DECISIONS.md`, риски — в `RISKS.md`.

## Архитектурная база

### ADR-010 — модульный монолит

- Статус: `ACCEPTED`
- Решение: один развёртываемый backend с модульными границами, общим PostgreSQL и явными application-портами.
- Причина: транзакционно связанная предметная область, ранняя стадия и отсутствие доказанной независимой нагрузки.
- Следствие: запрет на прямые импорты внутренних моделей между модулями; взаимодействие через application services и доменные события.
- Каждый доменный модуль владеет отдельной PostgreSQL schema и своими Alembic migrations. Другие модули не читают его таблицы напрямую и не используют его ORM-модели; ссылки между модулями передаются как ID через публичные application-порты.
- Межмодульное действие имеет один ведущий use case: он атомарно изменяет принадлежащее ему состояние и записывает outbox-факт. Реакции других модулей выполняются после commit и обязаны быть идемпотентными.
- Общий `shared kernel` содержит только технические типы и интерфейсы: идентификаторы, время, ошибки, event envelope и transaction abstractions. Общие доменные модели и бизнес-правила в нём запрещены.
- Путь выделения: чат, уведомления, media, рекомендации, AI-поиск и аналитика смогут стать сервисами после появления независимого масштаба или команды.
- Контекст: ожидаются десятки тысяч зарегистрированных пользователей, несколько разработчиков, адаптивный публичный сайт, Telegram Mini App и отдельная закрытая web-панель модератора. Все клиенты используют один backend API.
- Развёртывание нескольких процессов или контейнеров из одного репозитория не превращает систему в микросервисы: API, Celery worker и scheduler остаются частями модульного монолита.

### ADR-011 — упрощённые модули MVP

- Статус: `ACCEPTED`
- Я начинаю с семи крупных доменных модулей, а не с множества микросервисов:

| Модуль MVP | Ответственность |
|---|---|
| `accounts` | Telegram identity, внутренний User, публичный Profile, privacy/preferences |
| `discovery` | карта, поиск, категории, публичные projections, LookingPost |
| `events` | событие, location visibility, revisions, participation, capacity, waitlist и attendance MVP |
| `communication` | простой чат, публичные объявления, центр уведомлений, Telegram delivery и reminders |
| `trust_safety` | жалобы, премодерация, блокировки, апелляции, emergency и privileged audit |
| `reputation` | signal ledger, materialized projections, уровни, private policy adapter и trust integration |
| `media` | загрузка, metadata, safe processing, storage lifecycle |

- `admin` не является владельцем отдельной бизнес-логики. Это закрытый frontend/backend adapter, который с усиленной авторизацией вызывает разрешённые use cases перечисленных модулей.
- В MVP две административные роли:
  - `moderator` — очередь премодерации, проверка media/events, жалобы и временные меры в пределах выданных permissions;
  - `admin` — управление модераторами/permissions, постоянные ограничения, configuration, emergency escalation, апелляции и audited override.
- Даже при двух ролях backend проверяет отдельные permissions, а не условие `role == admin`; это позволит позднее добавить support/senior/superadmin без переписывания use cases.
- Дополнительные роли не включаются в MVP; их обязанности временно выполняет `admin` в пределах audited permissions.
- Игровые медали, достижения и challenges не смешиваются с репутацией. После MVP они получают отдельный модуль `achievements`; профиль только объединяет безопасные projections обоих модулей.
- Причина: публичная репутация входит в MVP и имеет отдельный ledger/policy/lifecycle, а admin является интерфейсом управления, а не предметной областью.
- Публичная карта и карточки читают только безопасную discovery projection/read model. Обычные обновления доходят до неё через versioned domain facts, но блокировка, удаление и скрытие по safety-причине немедленно закрывают публичную выдачу по fail-closed правилу.
- Только `trust_safety` владеет банами, ограничениями, safety-жалобами и предупреждающими safety-отметками. `reputation` вычисляет надёжность и не может самостоятельно блокировать аккаунт или событие.
- `media` владеет загрузкой, безопасной обработкой и lifecycle файла. Модуль-владелец объекта (`events` или `accounts`) хранит только `attachment_id`, роль файла и порядок отображения.

### ADR-012 — разделённая модель участия

- Статус: `ACCEPTED`
- Решение: не использовать один `EventMembership.status` для всех фактов.
- Записи:
  - `EventInterest` — слабое намерение и подписка на изменения;
  - `EventParticipation` — занятое место, добровольный выход или исключение;
  - `WaitlistEntry` и `WaitlistOffer` — очередь и временная резервация места;
  - `AttendanceCodeRedemption` — факт корректного ввода системного кода в MVP;
  - `AttendanceDecision` — предварительная неявка, 24-часовой спор и окончательный итог.
- `ParticipationConfirmation` отсутствует: вступление сразу занимает место, а критический перенос не требует нового действия.
- Повторное вступление создаёт новый episode участия. Для пары `user_id + event_id` одновременно разрешён только один активный episode; итоговое влияние на репутацию ограничивается одним результатом события, чтобы выходами и повторными вступлениями нельзя было умножить штраф или награду.
- При освобождении или добавлении нескольких мест система атомарно создаёт предложения первым `N` подходящим пользователям FIFO-очереди. Каждое место резервируется отдельно на обычный timeout из PD-006; пропущенное предложение переходит следующему.
- После окончания отсутствие успешного кода создаёт предварительный статус `не подтверждено` без немедленного влияния на репутацию. Пользователь получает уведомление и 24 часа на спор: выбирает причину и может добавить короткое пояснение. Организатор может ответить, но окончательное решение принимает moderator: `подтверждено`, `нейтрально` или `неявка`. Без спора предварительный статус становится окончательной неявкой.
- Причина: пользователь может поставить лайк, затем занять место или ждать его, выйти и позднее иметь отдельный результат посещения. Один enum не может честно ответить на все эти вопросы.
- Изменение спецификации: потребуется согласованное уточнение §24.2 и Приложения A.

### ADR-013 — версионирование события

- Статус: `ACCEPTED`
- Решение: `Event` хранит текущий lifecycle, а существенные изменения создают неизменяемую `EventRevision`.
- Причина: перенос времени должен оставлять доказуемую историю и отменять уведомления, запланированные для старых условий.
- После публикации дата, начало и окончание имеют общий лимит в два изменения. Одно сохранение с несколькими изменёнными временными полями считается одним переносом; после второго переноса дальнейшие изменения этих полей запрещены.
- Точка, адрес и категория после публикации неизменяемы. Если место больше не подходит, событие отменяется и создаётся заново.
- Смена режима видимости того же точного адреса разрешена и не расходует лимит переноса, потому что координата и адрес при этом не меняются.
- Место участника относится к событию и сохраняется при новой revision.
- Уведомление об изменении отправляется через Telegram-бота. Оно также сохраняется во внутреннем центре уведомлений и показывается при открытии приложения, если Telegram-доставка не состоялась.
- Предыдущие версии описания после публикации временно сохраняются для рассмотрения жалоб и модерации, но не показываются пользователям как публичная история.
- Одновременно существует не больше одной ожидающей модерации revision. Новое сохранение организатора заменяет его ещё не рассмотренный черновик; публичной остаётся последняя одобренная версия.
- Для переноса времени организатор обязательно выбирает нормализованную категорию причины и при желании добавляет короткое пояснение. Участникам показывается только безопасная причина без внутренних moderation-данных.
- Клиент передаёт ожидаемую версию агрегата. Устаревшее редактирование отклоняется как конфликт и никогда молча не перезаписывает более новую revision.
- Подробные старые/новые значения и свободный текст revision хранятся 90 дней, затем удаляются. Долгосрочно остаются компактные факты: число переносов, величина сдвига, critical/late flag и категория причины.
- Следствие: критические изменения, публикация, отмена и moderation hold идемпотентны и записываются в audit/domain-event ledger.

### ADR-014 — PostgreSQL + PostGIS с первого функционального среза

- Статус: `ACCEPTED`
- Решение: PostgreSQL — источник истины; координата — `geography(Point, 4326)` с GiST-индексом.
- Причина: bounding box карты, границы поддерживаемых городов, точки событий и будущие географические функции являются частью ядра продукта.
- Модель места:
  - адрес, полученный reverse geocoding по выбранной точке;
  - нормализованный адрес;
  - выбранная пользователем точка;
  - точка, предложенная провайдером;
  - provider name/place id;
  - locale/region;
  - precision/confidence;
  - `location_visibility`;
  - canonical street ID и официальная опорная точка улицы для общей street marker-плашки;
  - необязательный ориентир организатора длиной до 20 символов.
- Ручной ввод и текстовый поиск адреса в MVP отсутствуют. Выбранная метка является источником истины, Nominatim только объясняет её адресом.
- Адрес/координата пользователя и `UserDiscoveryLocation` в MVP отсутствуют: сохраняется только выбранный `city_id`.
- После ручного перемещения метки выбранная точка является авторитетной; reverse geocoding формирует адрес по ней и не двигает метку обратно.
- Точная точка события хранится всегда. Неавторизованная для неё выдача получает только улицу и общую street marker-плашку, но не получает ложную координату конкретного события.
- Кластеризация точных и street markers не используется в MVP и добавляется только после появления измеримой плотности.
- Публикация события разрешена только внутри утверждённого полигона поддерживаемого города. Спорные окраины и изменение границы администратор проверяет и корректирует вручную.
- Общая street marker использует заранее рассчитанную стабильную опорную точку геометрии улицы. Она не зависит от количества или координат отдельных событий и не изображает ложное место встречи.
- Точные координаты остаются доступны PostGIS для серверных проверок. Они защищаются закрытой сетью, отдельными минимальными DB-правами, шифрованием диска и backups и запретом попадания в логи; отдельное application-level шифрование поля в MVP не вводится.

### ADR-015 — transactional outbox до внешнего брокера

- Статус: `ACCEPTED`
- Решение: domain event и изменение бизнес-состояния записываются одной транзакцией в PostgreSQL; отдельный worker доставляет внешние эффекты.
- Причина: устраняет окно «событие сохранено, уведомление потеряно».
- MVP: outbox-таблица, lease/`FOR UPDATE SKIP LOCKED`, уникальный `fact_id`, idempotency key, exponential backoff с ограничением и dead-letter status.
- Успешное бизнес-действие не откатывается из-за временной недоступности Redis, Celery или Telegram: запись остаётся в outbox и доставляется позднее.
- У временного уведомления есть `expires_at`; после истечения оно не отправляется. Бизнес-факты, reputation signals и обязательный security audit по этому правилу не удаляются.
- Перед выполнением эффекта worker проверяет текущую `aggregate_version` и актуальность задачи. Устаревшее уведомление или пересчёт пропускается с зафиксированной причиной; обязательные факты одного агрегата обрабатываются последовательно.
- Retry policy задаётся по типу задачи: разные пределы попыток, backoff с jitter и срок актуальности. Один бесконечный или одинаковый retry-режим для всех задач запрещён.
- Автоматические повторы ограничены. Неисправимая либо исчерпавшая попытки актуальная задача получает dead-letter status и доступна только `admin` в закрытой панели.
- Администратор может повторить только актуальную идемпотентную задачу. Редактирование payload, получателя и системных идентификаторов запрещено; массовый повтор требует отдельного подтверждения. Все действия записываются в privileged audit.
- Технические Telegram-оповещения отправляет отдельный закрытый operations bot:
  - критические dead-letter и задачи, требующие ручного действия, отправляются сразу;
  - некритические dead-letter объединяются в digest;
  - временные ошибки в процессе автоматических retry в бот не отправляются;
  - получатели — только активные `admin` с permission `ops_alerts.receive`;
  - сообщение содержит только безопасный тип/критичность, opaque ID/trace ID и ссылку на закрытую панель;
  - точные адреса, персональные данные, секреты, токены, приватный контент и полный payload запрещены.
- Operations bot не выполняет административные команды и не повторяет задачи: все действия доступны только после усиленной авторизации в закрытой web-панели.
- Токен operations bot хранится только в secret storage/runtime environment и никогда не попадает в публичный Git, логи или клиентский код.
- После устранения dead-letter безопасный технический payload хранится 30 дней. Нормализованные тип, результат, время решения и audit-факт хранятся 90 дней; PII и полный внешний payload в dead-letter не копируются.
- Kafka: может быть добавлена как транспорт outbox позже без изменения бизнес-транзакций.

### ADR-016 — итоговая проекция события вместо полного event sourcing

- Статус: `ACCEPTED`
- Решение: текущая запись `Event` после завершения становится каноническим итоговым снимком; отдельная копия всех её полей не создаётся. Нормализованные `ParticipationOutcome`, `EventRating` и reputation/achievement ledger сохраняют связи и итоговые результаты.
- Итоговая запись сохраняет точный адрес с прежней классификацией доступа. Он не заменяется геоячейкой, не становится публичным и не копируется в отдельный аналитический набор.
- Существенные изменения времени, места, lifecycle и moderation могут храниться в ограниченном `EventRevision/AuditEvent`; обычные правки текста после compaction удаляются.
- Для отклонённых и заблокированных объектов сохраняются факт и нормализованная причина решения. Фотографии и другой тяжёлый контент не входят в долгосрочную проекцию.
- LookingPost использует ту же модель: текущая запись становится итоговой, полезные факты и связь `looking_post_id → event_id` сохраняются, а текст, media и временные записи удаляются по срокам.
- Причина: сохраняется доказуемая история важных действий без дублирования всего события и бесконечного роста таблицы revisions.
- Следствие: очистка должна быть идемпотентной, иметь `compacted_at`, `compaction_version` и reconciliation-проверку; агрегаты всегда можно сверить с сохранёнными итоговыми фактами.
- Очистка выполняется по классам данных, а не одним общим удалением: чат — через 24 часа, media — через 7 дней, attendance evidence — через 30 дней после спора, moderation/privileged audit — через 90 дней. Итоговая нормализованная проекция хранится отдельно от этих временных деталей.
- Публичная итоговая карточка завершённого или отменённого события показывает место максимум до улицы, даже если во время события точный адрес был публичным. Защищённый точный итоговый адрес остаётся только во внутренней записи с прежними серверными правами.
- Истёкшая или завершённая публикация LookingPost по deep link показывает только статус без старого текста и контактов. Автору доступны безопасные итоговые счётчики и связь с созданным событием.

### ADR-017 — Kafka-ready без Kafka в MVP

- Статус: `ACCEPTED`
- Я не запускаю Kafka в MVP, но не связываю бизнес-логику с PostgreSQL polling, Celery или конкретным брокером.
- Каждый важный доменный факт имеет стабильные `fact_id`, `fact_type`, `aggregate_id`, `aggregate_version`, `occurred_at`, `schema_version`, correlation/causation IDs и типизированный payload. ID пользовательского события передаётся отдельно как `subject_event_id`.
- Event envelope сериализуется в JSON, а payload каждого `fact_type` проверяется отдельной версионируемой Pydantic-схемой. Неограниченный `dict[str, Any]` внутри доменного контракта запрещён.
- Совместимые изменения только добавляют необязательные поля и не меняют смысл существующих. Несовместимое изменение получает новую `schema_version`; на переходный период consumers поддерживают текущую и предыдущую версии.
- Изменение бизнес-состояния и outbox-запись фиксируются одной транзакцией PostgreSQL. Celery-задача является тонким adapter: она получает идентификатор и вызывает application use case, а не содержит бизнес-правила.
- Будущий Kafka publisher читает тот же outbox. Подключение Kafka меняет delivery adapter и deployment, но не use cases, модели или правила предметной области.
- Для решения о подключении Kafka я измеряю:
  - возраст и размер очереди outbox;
  - скорость создания и доставки событий;
  - количество независимых consumers одного события;
  - нагрузку PostgreSQL от fan-out/polling;
  - потребность в replay и независимой аналитике;
  - retries, duplicate rate и consumer lag.
- Kafka рассматривается, когда появляются несколько независимых consumers, нужен replay либо outbox/DB становится измеримым узким местом.
- Медленный SQL-запрос, тяжёлая обработка фото или нехватка CPU сами по себе не являются причиной добавлять Kafka.
- Kafka не используется как broker Celery: по актуальной документации Celery этот transport имеет experimental status; для Celery выбран stable Redis transport.
- Kafka подключается только после подтверждения метриками, назначения ответственного за эксплуатацию, отдельного нового ADR и моего явного разрешения.

### ADR-018 — поэтапное физическое разделение серверов

- Статус: `ACCEPTED`
- На старте у меня один физический сервер. Компоненты разделены контейнерами и приватными сетями, поэтому позднее их можно переносить по одному без изменения бизнес-логики.

| Этап | Физические серверы | Размещение |
|---|---:|---|
| Разработка | 1 компьютер | Docker Compose: frontend, API, Celery worker/beat, PostgreSQL/PostGIS, Redis, Nominatim и локальное media storage |
| MVP/alpha | 1 сервер | Docker Compose: reverse proxy, публичный frontend, Mini App frontend, admin frontend, API, Celery worker/beat, PostgreSQL/PostGIS, Redis и закрытый Nominatim в отдельных контейнерах |
| Первый рост | 2 сервера | сервер 1: proxy/frontends/API/Celery/Redis; сервер 2: PostgreSQL/PostGIS |
| Рост фоновой нагрузки | 3 сервера | сервер 1: proxy/frontends/API; сервер 2: Celery/Redis/media processing; сервер 3: PostgreSQL/PostGIS |
| Высокая доступность | 4+ | минимум два API instances за load balancer, отдельные workers, PostgreSQL и Redis; Kafka добавляется только по ADR-017 |

- На одном сервере наружу открыты только `80/443`; PostgreSQL и Redis доступны только внутренней Docker-сети.
- MVP/alpha сознательно использует Docker Compose на одном сервере. Kubernetes рассматривается только после появления нескольких серверов/instances и реальной потребности в scheduling или high availability.
- Media хранится в защищённой локальной директории файловой системы за заменяемым `MediaStorage` adapter; binary-файлы не кладутся в PostgreSQL. Каталог не раздаётся напрямую и переносится в S3-compatible storage без изменения доменной логики.
- Для alpha принято `RPO ≤ 24 часа` и `RTO ≤ 24 часа`. Это осознанный недорогой уровень восстановления; encrypted off-server backup и регулярная проверка восстановления обязательны.
- Nominatim получает отдельный закрытый контейнер, volume, healthcheck и resource limits, чтобы импорт или reverse geocoding не мог бесконтрольно вытеснить API/PostgreSQL на первом сервере.
- Даже на первом этапе резервные копии базы и media должны уходить за пределы этого сервера, иначе его поломка уничтожит и данные, и backup.
- Следующий сервер добавляется не по календарю, а по причине:
  - база упирается в RAM/IO или требует отдельного backup/failure domain — первой выносится PostgreSQL;
  - Celery/media забирают CPU/RAM и замедляют API — первым выносится worker;
  - API упирается в CPU/connections — добавляется второй API instance и load balancer.
- Предлагаемые origins: публичный сайт — основной домен, интерактивное приложение — `app`, API — `api`, закрытая модерация — `admin`. Точные домены задаются перед deployment.

### Python 3.14

- Рекомендация: остаться на обычном CPython 3.14, зафиксировать patch version/lock и тестировать Linux production image в CI.
- Не использовать `3.14t`: free-threaded runtime официально поддержан, но C-extensions могут включить GIL обратно; для I/O-bound API выгода не оправдывает новый профиль риска.
- Python 3.13 — только запасной runtime для отдельного worker, если выбранная очередь не пройдёт integration/soak tests на 3.14.
- Python 3.12 — только если конкретная обязательная production-зависимость или инфраструктурный поставщик документированно блокирует 3.13/3.14.
- Миграционный путь при fallback: не использовать синтаксис только 3.14 в shared domain package, вести CI matrix 3.13/3.14, возвращаться на 3.14 после прохождения контрактных и нагрузочных тестов.
- Источники: [Python 3.14.6](https://www.python.org/downloads/release/python-3146/), [free-threading limitations](https://docs.python.org/3/howto/free-threading-python.html), [FastAPI](https://pypi.org/project/fastapi/), [Pydantic](https://pypi.org/project/pydantic/), [SQLAlchemy](https://pypi.org/project/SQLAlchemy/), [asyncpg](https://pypi.org/project/asyncpg/), [Celery](https://pypi.org/project/celery/).

### Kafka, Celery и Redis

- В MVP я использую PostgreSQL outbox + Celery 5.6 worker/beat + Redis broker.
- Celery отвечает за выполнение конкретных задач; доменные правила остаются в application use cases.
- Redis хранит только очередь, rate limits и короткоживущий cache. Capacity, waitlist, права и другие бизнес-факты определяются только PostgreSQL.
- Kafka не запускается, но контракты событий и outbox соответствуют ADR-017.
- Kafka добавляется при нескольких независимо масштабируемых consumers, необходимости replay, измеримом event throughput или отдельной аналитической платформе.
- Kafka не подставляется как Celery broker: официальный Celery 5.6 отмечает Redis/RabbitMQ как stable transports, а Kafka transport — как experimental.
- FastAPI `BackgroundTasks` допустимы только для недолговечных, некритичных эффектов, потеря которых безопасна. Уведомления, начисления, архивирование и moderation workflow туда не помещать.
- Источники: [Celery task queues](https://docs.celeryq.dev/en/stable/getting-started/introduction.html), [Celery brokers](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/index.html).

### ADR-019 — карта и региональный геокодер

- Статус: `ACCEPTED`
- Map UI: MapLibre GL JS.
- В MVP браузер получает vector tiles напрямую с публичного OpenFreeMap. На текущих условиях сервис бесплатен, разрешает коммерческое использование, не требует регистрации/API key и не заявляет лимитов просмотров или запросов.
- Обязательные ограничения публичного OpenFreeMap:
  - видимая attribution OpenMapTiles/OpenStreetMap;
  - сервис предоставляется `as-is`, без SLA, персональной поддержки и гарантий точности или доступности;
  - сервис может быть изменён или прекращён без предварительного уведомления;
  - OpenFreeMap не предоставляет geocoding, поиск, маршруты, навигацию, спутниковые снимки или elevation;
  - незаконное, нарушающее работу сервиса и неразрешённое автоматизированное извлечение данных запрещены.
- URL style/tiles задаётся конфигурацией, а event markers загружаются только с моего API. Скрытые координаты и данные событий не передаются OpenFreeMap.
- Прямой публичный `tile.openstreetmap.org` не используется.
- Reverse geocoding выполняет собственный Nominatim 5.3.x с региональным OSM extract Дагестана. В MVP он работает как закрытый внутренний сервис на первом сервере; браузер обращается только к backend.
- До запуска региональные OSM-данные импортируются в отдельную поисковую базу Nominatim. Администратор вручную проверяет реальные точки стартовых городов, включая дома, улицы, окраины и неполные ответы; формального процента успешности или обязательного latency-порога для запуска нет.
- После первоначального импорта данные Nominatim в MVP не обновляются по расписанию. Администратор вручную запускает проверяемое обновление после обоснованных жалоб на адреса и перед добавлением нового города; неудачное обновление должно допускать rollback к предыдущему набору.
- Ручной ввод и текстовый поиск адреса отсутствуют. В центре карты находится условная event marker; через 500 мс после `moveend` backend выполняет reverse geocoding и показывает адрес. Новое движение отменяет ожидающий запрос, а устаревший ответ игнорируется.
- Координата метки является источником истины. Если дом не найден, точная координата сохраняется, адрес показывается частично, а организатор может заполнить необязательный короткий ориентир.
- Photon не входит в MVP и рассматривается только при подтверждённой потребности в текстовом поиске с устойчивыми к опечаткам подсказками.
- После MVP я разворачиваю собственные региональные vector tiles на отдельном сервере, не на основном application server. MapLibre переключается на них через конфигурацию без изменения frontend/business logic.
- Собственный tile server получает обновления OSM по регламенту, имеет monitoring, cache, резерв по диску/трафику и проверенный rollback набора tiles. При дальнейшем росте перед ним можно добавить CDN.
- До готовности собственного tile server сохраняется аварийная возможность переключить `MAP_STYLE_URL` на совместимый источник.
- «Бесплатно» означает отсутствие платы за API/лицензию; собственный Nominatim всё равно требует CPU, RAM, disk, обновлений и monitoring.
- Источники: [OpenFreeMap](https://openfreemap.org/), [OpenFreeMap Terms](https://openfreemap.org/tos/), [MapLibre](https://maplibre.org/), [Nominatim Reverse](https://nominatim.org/release-docs/latest/api/Reverse/), [Nominatim regional extracts](https://nominatim.org/release-docs/latest/admin/Import/), [Photon](https://github.com/komoot/photon).

## Telegram-интеграция

### ADR-020 — Telegram как identity provider, не доменная модель

- Статус: `ACCEPTED`
- Решение: внутренний immutable `user_id` отделён от внешней Telegram identity. События, участие, репутация, профиль и права ссылаются только на внутренний `user_id`.
- Защищённая identity-запись хранит уникальный `telegram_user_id`, проверенные OIDC `issuer + subject`, факт запуска/доступности пользовательского бота и timestamps первой/последней успешной авторизации. Telegram username, имя и фото не являются идентификаторами.
- Сервер принимает только подписанный `initData`, проверяет HMAC/Ed25519 согласно режиму, `auth_date`, допустимое окно, replay nonce/session binding. `initDataUnsafe` не доверяется.
- Bot webhook проверяет `X-Telegram-Bot-Api-Secret-Token`, update id дедуплицируется.
- Deep link содержит короткий непрозрачный signed/lookup token, срок и назначение; не содержит PII, координаты или права доступа.
- На обычном сайте используется официальный Telegram OIDC Authorization Code Flow с PKCE; backend проверяет подпись ID token через JWKS, `iss`, `aud`, `exp`, `state` и nonce. Разрешённые origin/callback URLs заранее регистрируются в BotFather.
- Обычный вход сайта запрашивает только `openid` и `profile`. Scope `phone` и bot write access при входе не запрашиваются; номер телефона не нужен и не сохраняется.
- Для связывания website OIDC и Mini App сохраняются проверенные `issuer + sub` и подписанный Telegram `id` из `profile`; отдельный внутренний профиль для сайта не создаётся.
- Telegram name, username и picture из проверенного token/initData не копируются в публичный профиль и не перезаписывают его. Afisha создаёт случайный псевдоним, а аватар пользователь загружает самостоятельно.
- Mini App открывается через уже запущенного пользовательского бота, поэтому отдельный запрос разрешения на сообщения не показывается. Пользователь сайта, который ещё не запускал бота, получает все функции без ограничений.
- При первом важном действии на сайте, например вступлении или создании события, можно один раз ненавязчиво предложить открыть бота через безопасную deep link ради критических уведомлений. Отказ не блокирует действие; до `/start`, после блокировки бота или при ошибке доставки уведомление остаётся во внутреннем центре и критическом banner fallback.
- В MVP нет ручного восстановления или переноса профиля на другой Telegram-аккаунт. Потеря или удаление Telegram-аккаунта означает отсутствие доступа к связанному профилю; support/admin не связывает новый Telegram ID со старым аккаунтом.
- Website после проверки Telegram identity создаёт отзываемую rolling-сессию на 30 дней с абсолютным сроком 90 дней. Mini App создаёт сессию на 24 часа и незаметно обновляет её после проверки свежего `initData`. Пользователь может завершать свои website/Mini App sessions.
- Закрытая web-панель не использует Telegram identity пользователя. Для `moderator` и `admin` действуют отдельные логины и пароли, отдельная cookie/session namespace и отдельный authentication flow.
- Саморегистрации сотрудников нет. Администратор отправляет одноразовое ограниченное по времени приглашение для установки пароля; сброс выполняет другой администратор. Первая главная учётная запись создаётся одноразовой серверной командой.
- Пароль хранится только как Argon2id hash. Административная сессия действует максимум 8 часов, завершается после 30 минут бездействия, а опасные операции требуют повторного ввода пароля.
- Вход панели защищён rate limit, общими сообщениями об ошибке без раскрытия существования логина, CSRF-защитой, `Secure`/`HttpOnly`/подходящим `SameSite` cookie и audit выдачи роли, входов, неудачных попыток, сбросов и повторной проверки.
- Raw `initData`, authorization code, ID/access token, client secret, bot token, пароль и session cookie не записываются в application logs.
- Пользовательский bot и operations bot имеют разные tokens, webhook secrets, разрешённые сценарии и update deduplication. Operations bot не участвует в авторизации пользователей.
- Источники: [Telegram Mini Apps](https://core.telegram.org/bots/webapps), [Log In With Telegram / OIDC](https://core.telegram.org/bots/telegram-login), [Bot API webhook](https://core.telegram.org/bots/api#setwebhook), [Bot limits](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this), [deep links](https://core.telegram.org/api/links).

## Инженерные правила до реализации

1. HTTP route выполняет transport validation и вызывает один application use case; SQL/Redis/Kafka/Telegram SDK в route запрещены.
2. ORM-модели не содержат orchestration и внешних побочных эффектов.
3. Межмодульные зависимости направлены через публичные порты; CI проверяет запрещённые импорты.
4. Внутренние команды/результаты типизированы; `dict[str, Any]` допустим только на адаптерной границе с немедленной валидацией.
5. Статусы — enum/value objects; неизвестный внешний статус обрабатывается явно.
6. Все команды изменения имеют idempotency key; webhook/outbox consumer хранит inbox/dedup record.
7. Все списки пагинируются; map API использует viewport/bbox, limit и server clustering strategy.
8. Все внешние вызовы имеют timeout, bounded retry, jitter и circuit-breaker policy; бесконечные retry запрещены.
9. Capacity, waitlist offer и join выполняются транзакционно с row/advisory lock или атомарным SQL constraint.
10. Файлы имеют лимиты размера/типа/пикселей, проходят decode/re-encode и удаление EXIF; исходник не становится публичным до премодерации.
11. Миграция обязательна для каждого schema change; downgrade/forward-fix strategy и migration test входят в PR.
12. Security/audit events append-only; репутация и достижения выводятся из ledger и корректируются compensating entries.
13. Media decoder — Pillow или совместимая open-source библиотека; изображение полностью декодируется, ограничивается по пикселям, меняет ориентацию, пересохраняется в WebP/JPEG и теряет исходные metadata.
14. Текущий reputation projection обновляется событием; immutable history остаётся источником восстановления, но не читается при каждом показе профиля.
